# 多租户电商 SaaS 后续开发任务规划

> 适用阶段：电商后端 MVP 主链路完成之后  
> 建议周期：12～16 周，可按业余时间延长  
> 核心原则：先跑通业务闭环，再提升可靠性，最后做扩展与部署

## 1. 当前基线

目前已经完成：

- pnpm + Turborepo Monorepo
- Gateway 与 Core 模块化单体
- 租户、套餐、配额、RBAC、审计与 PostgreSQL RLS
- 管理员登录、JWT Access Token、Refresh Token 轮换
- 分类、品牌、商品、SKU、库存流水
- 订单快照、幂等下单、库存锁定、取消和超时关闭
- 支付单、Mock 支付、微信支付 v3 下单基础设施
- 微信回调验签、解密、Inbox、重试和死信
- PostgreSQL、Redis、MinIO 本地基础设施
- 商品 → 库存 → 订单 → 支付 → 出库的真实数据库 E2E
- B1 发货与物流：整单/部分发货、物流单、租户 RLS、发完自动进入 `fulfilled`
- B2 第一阶段：退款申请、服务端金额计算、数量上限与人工审核状态机

> 2026-08-28 进度说明：渠道退款、退款回调和退款成功后的库存流水仍属于 B2 下一阶段；
> `20260827000200_shipments` 与 `20260828000100_refunds` 迁移需在目标开发数据库执行后，
> 再开启 `RUN_DATABASE_E2E=true` 验证完整数据库链路。

当前系统更接近“后端业务骨架”，还缺少用户能直接使用的管理后台、小程序、客户体系，以及生产环境能力。

## 2. 总体路线

```text
阶段 A：前端可用
管理后台 + 小程序 + 客户登录 + 购物车
        ↓
阶段 B：交易完整
收货地址 + 配送 + 发货 + 售后退款 + 对账
        ↓
阶段 C：平台可靠
事件总线 + Outbox + 可观测性 + 限流 + 数据备份
        ↓
阶段 D：SaaS 扩展
租户装修 + 行业包 + Webhook + 开放 API
        ↓
阶段 E：生产交付
CI/CD + 部署 + 安全加固 + 压测 + 灾备演练
```

## 3. 阶段 A：做出真正可操作的产品（建议 4 周）

### A1. 管理后台基础壳

目标：商家管理员可以登录并进入自己的工作台。

任务：

- 新建 `apps/pc-admin`
- Vue 3 + TypeScript + Vite + Element Plus + Pinia + Tailwind CSS
- 登录、刷新令牌、退出登录
- API Client、统一错误处理、请求 ID 展示
- 路由权限和按钮权限
- 租户套餐、到期状态和配额展示
- Layout、侧边栏、顶部租户信息

验收：

- 未登录不能访问后台页面
- Access Token 过期后可以无感刷新一次
- 无权限菜单和操作按钮不可见
- 租户冻结或过期时，页面能解释不可操作原因

### A2. 商品管理后台

目标：商家可以完整维护商品数据。

任务：

- 商品列表、搜索、状态筛选、游标分页
- 新建和编辑商品
- SKU 动态表单
- 分类与品牌管理
- 上架、归档操作
- 乐观锁冲突提示
- 图片上传到 MinIO

验收：

- 表单金额始终使用字符串，不能产生浮点误差
- 编辑过期版本时正确展示冲突
- 上传失败可重试，不产生无引用文件
- 列表、创建、编辑流程均有加载、空、错误状态

### A3. 小程序商品列表与详情

目标：消费者可以在小程序中浏览当前租户已经上架的商品和 SKU。

建议技术：

- uni-app + Vue 3 + TypeScript
- Pinia 管理客户端状态
- 通过统一 API Client 管理服务端数据访问
- 复用 `@saas/contracts`

任务拆分：

1. 新建 `apps/miniapp`
2. 配置 Monorepo workspace、TypeScript、Lint、构建命令
3. 实现租户识别：开发环境配置租户，生产环境按小程序/域名映射
4. 封装 API Client，自动附带租户信息和请求 ID
5. 商品列表：搜索、分类筛选、加载更多、空状态
6. 商品详情：商品快照、SKU 选择、价格和库存展示
7. 骨架屏、错误页、重试按钮
8. 将已选 SKU 加入本地购物车
9. 为 SKU 选择和购物车写单元测试

验收标准：

- 只展示 `active` 商品
- 切换 SKU 后价格和可售库存同步变化
- 游标分页不重复、不漏项
- 网络失败后可以手动重试
- 不在组件里直接调用 `fetch`
- 页面不依赖数据库字段，只依赖共享契约
- `pnpm check` 能覆盖 miniapp

你会练到的技术：

- Monorepo 新应用接入
- 前后端共享 TypeScript 类型
- 服务端状态与客户端状态的边界
- 小程序生命周期和分包
- SKU 组合选择算法
- 多租户请求上下文
- 可测试的前端架构

建议开发顺序：

```text
项目启动
→ 静态商品列表
→ 接真实接口
→ 商品详情
→ SKU 选择
→ 库存展示
→ 本地购物车
→ 测试与异常状态
```

### A4. 客户身份与地址——预留给你亲自开发

目标：消费者拥有独立于管理员的身份体系。

任务：

- 设计 Customer、CustomerIdentity、CustomerSession、Address 数据模型
- 编写 Prisma Migration，并为租户表启用和强制执行 RLS
- 按 domain → application → infrastructure/interfaces 建立 customer 模块
- 定义 `CustomerIdentityProvider` 端口
- 实现 Mock 登录适配器，之后再实现微信 `code2Session` 适配器
- 签发独立的客户 Access Token 和可轮换 Refresh Token
- OpenID/Provider User ID 在租户和渠道内唯一
- 收货地址 CRUD、默认地址和归属校验
- 客户端接口与管理员接口权限隔离
- 为领域规则、Token 轮换、RLS 和越权访问编写测试

验收：同一个 OpenID 在不同租户中不能串数据，客户令牌不能访问后台管理接口。

这个任务适合从前端转向后端，因为它会同时练习：

- 关系数据库建模、唯一约束和索引
- Prisma Client、Migration 与事务
- NestJS Module、Controller、Service 与依赖注入
- 端口/适配器模式，避免业务层绑定微信 SDK
- 密码学 Token、会话轮换和撤销
- 多租户 RLS 与对象级越权防护
- 单元测试、数据库集成测试和 HTTP E2E

建议实现顺序：

```text
领域模型与契约
→ Prisma Schema 与 Migration
→ Mock 身份提供方
→ 客户登录与 Access Token
→ Refresh Token 轮换
→ 地址 CRUD
→ RLS 与越权测试
→ 微信 code2Session 适配器
```

### A5. 购物车与提交订单

目标：小程序可以从购物车创建真实订单。

任务：

- 本地购物车第一版，后续增加服务端购物车
- 提交前重新获取服务端价格与库存
- 防重复点击的幂等键
- 地址快照、商品快照、价格明细
- 下单成功页和支付倒计时
- Mock 支付完整交互

验收：客户端篡改价格无效；连续点击提交只创建一张订单。

## 9. 你的任务如何开始

先不要一次把整个 A4 写完。你的第一轮只做“客户模型 + Mock 登录”，暂时不做微信联网和地址管理：

1. 在 `packages/contracts` 定义客户登录请求与响应
2. 在 Prisma Schema 中设计 `Customer` 和 `CustomerIdentity`
3. 手写新的 Migration SQL，并加入 RLS Policy
4. 新建 `apps/core/src/customer` 模块和空的分层目录
5. 实现 Mock 登录：输入一个测试身份标识，返回或创建对应客户
6. 暂时只返回客户资料，不签发 Token
7. 编写领域规则单元测试和真实 PostgreSQL RLS 测试
8. 确保 `pnpm check` 和数据库 E2E 通过

第一轮完成后，再实现客户 JWT 与 Refresh Token。这样可以先把“数据模型和租户隔离”学扎实，再进入密码学和会话安全。

第一轮明确不做：

- 微信 `code2Session`
- Refresh Token
- 收货地址
- 小程序页面
- 第三方登录 SDK

这些不是删掉，而是留到后续迭代，避免第一个后端任务范围失控。

## 10. 每个任务的完成定义

任务只有同时满足以下条件才算完成：

- 功能满足验收标准
- 正常、空、错误、无权限状态均有处理
- 不绕过租户隔离、权限和共享契约
- 至少覆盖关键领域规则或交互测试
- `pnpm check` 通过
- README 或对应文档已更新
- 代码中没有真实密钥、测试账号密码或生产地址

## 11. 遇到问题时的协作方式

你开发 A4 时，可以把问题按下面格式发给我：

```text
目标：我正在实现 CustomerIdentity 的租户内唯一约束
现象：不同租户使用相同 Mock 身份时创建失败
我尝试过：给 providerUserId 添加 unique
相关文件：db/schema.prisma
希望你做：只帮我定位原因，先不要直接修改
```

如果你希望我直接修复，把最后一行改为“请修改并解释原因”。这样你可以控制我是做导师、Code Review，还是直接协作开发。
